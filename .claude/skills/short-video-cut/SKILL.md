# 短影音自動剪輯技能

把「一支原始長錄影」變成「一支剪好、燒好字幕、配好 B-roll 的 9:16
短影音」。整套邏輯分成三層，只有中間「判斷」的部分會用到你（AI）的
推理能力，其餘兩層都是本機程式在做，不要自己重新發明：

1. **辨識層**（不耗推理）：`new_project.py` 呼叫 Groq API／
   faster-whisper／openai-whisper 把語音轉成逐句 SRT ＋逐字時間戳
   `.words.json`，純本機或雲端 API 運算，不吃你的推理。
2. **判斷層**（耗推理，這是你的工作）：讀逐字稿，決定要剪哪些片段、
   下什麼標題、配什麼 B-roll 關鍵字、字幕怎麼分句，寫進
   `06_meta/edit_state.json`。
3. **執行層**（不耗推理）：`render.py` 讀 `edit_state.json`，實際呼叫
   ffmpeg／ImageMagick 剪片、燒字幕（ASS/libass）、貼字卡、混音，
   全部是明確指令，不要用推理去「模擬」剪輯結果。`verify_render.py`
   是這層的驗證工具：出片後重新轉錄成品、比對字幕時間有沒有偷跑，
   見第 5.5 步，每次出片後都要跑，不是選配。

> **維護守則**：這份技能檔要跟著 `render.py`／`caption_editor/` 的
> 實作同步更新。之前發生過連續好幾輪迭代（GUI 逐字編輯、
> `source_start`/`source_end`、版本化輸出、字卡雙行上色…）都只改了
> 程式碼、沒回頭改這份文件，導致整份指南跟實際架構脫節（例如還在講
> 早已拿掉的 PNG 逐句字幕疊圖法）。**核心流程或 schema 有實質變動時，
> 這份檔案要一起改**；瑣碎的技術眉角（顏色格式、Windows 換行符號等）
> 直接看 `README.md`「已知的技術眉角」，不要在這裡重複
> 維護第二份、之後又對不上。

## 何時觸發

使用者提到「有一支錄好的影片」「幫我剪短影音」「用剪短影音的技能」
等語句時，啟動這個 Skill。

## 標準流程

### 第 1 步：確認來源影片

先確認影片檔案存在、格式、大小。不要假設檔名，一定要先確認過再
繼續。原始影片通常較大，複製/搬移前先跟使用者說一聲。

### 第 2 步：一次問完使用者三件事

在建立專案之前，一次問清楚，不要分次問：

1. **剪輯模式**：「行銷短影音」還是「教育版」？（見下方「兩種剪輯
   模式」）
2. **這一集的主題**（用來命名專案資料夾）。使用者還沒想好的話，
   提議先用暫定名稱（例如來源檔名）開跑，字幕轉出來後再改，避免
   卡住流程。
3. **要不要配 B-roll？密集程度多高？** B-roll 是 Claude 用 Pexels
   API 找、下載；配樂則是使用者自己準備音檔給 Claude，不是 Claude
   去網路上找。B-roll 只在使用者要求時才加，不要預設加。要加的話
   進一步問密集程度（例如「每個重點片段都配一段」還是「只在少數
   關鍵句配」、整體大概想要幾段），不要自己猜一個數量下去抓，密度
   太高會喧賓奪主、太低又等於沒配。

### 第 3 步：建立專案並轉字幕

呼叫 `new_project.py`（不要自己重寫這段邏輯）：

```bash
cd "<你 clone 這個 repo 的路徑>" && \
python new_project.py "<原始影片完整路徑>" --name "<專案名稱>"
```

這一步會建立六個子資料夾（見下方「資料夾結構」），把原始影片複製
進 `01_source/`，並依序嘗試 Groq API（設了 `GROQ_API_KEY` 才會用，
最快）→ faster-whisper（本機 CPU）→ openai-whisper CLI（最後備援），
輸出 `02_transcript/*.srt` 與逐字時間戳 `*.words.json`（中文已經過
`opencc` 簡轉繁）。影片較長時這步要跑幾分鐘，跑之前先跟使用者說明
預估時間，背景執行、不要乾等卡住對話。

### 第 4 步：讀逐字稿，判斷剪輯點與內容重點

讀 `02_transcript/*.srt`（需要更精確的斷點時用 `.words.json`），
做這些判斷（這是你真正該花心力的地方）：

- **行銷短影音**：**不要讀完逐字稿就直接選定一組片段去寫
  `edit_state.json`／出片**——這是踩過的坑：AI 自己選一版直接出片，
  使用者不滿意的話，後面只能一輪一輪靠使用者事後挑毛病、你再改，
  來回成本很高。正確順序分兩階段：
  1. **先整理主題**：通篇讀過逐字稿，列出這支影片有哪幾個主題／
     段落、各自在講什麼、大致的時間區間（跟教育版第一步做的事
     一樣，只是行銷版不用讓使用者選主題，是你自己拿來規劃精華版
     用的素材庫）。
  2. **再提 2-5 套不同的精華版剪輯方案供使用者選**，不要只準備
     一套。每套方案簡述：選了哪幾個片段（對應到上面整理出的主題／
     時間點）、大致故事線邏輯、預估總長度，讓使用者用
     `AskUserQuestion` 或條列文字選一套（也可以「都不要，另外討論」）
     ——使用者選定或調整方向之後，才進入抓 3-5 個最精簡有力的片段
     （可以互相不連續）、拼成 30-60 秒重點精華版、寫
     `edit_state.json` 的實際動作。故事線要完整（問題→構想→解法→
     結論這種節奏，或依主題整理結果調整）。
- **教育版**：先分析逐字稿有哪些主題，讓使用者多選要哪幾個主題，
  選定的主題**保留完整解說**（不抓重點），只剪掉停頓、明顯贅詞/
  重複、離題的閒聊——長度通常會到幾分鐘，不是短影音的長度。
- 兩種模式都是同一套 `clips[]` 機制（`{start, end, keep, reason}`
  交錯），差別只在你怎麼決定要保留哪些時間區間。
- 擬一個吸睛的標題（`title.text`，可以用 `\n` 分兩行分開上色）。
- 抓 2-4 個適合配 B-roll 的關鍵字（英文，Pexels 查詢用英文效果
  較好），標出對應的時間區間——只在使用者第 2 步要求時才做。
- `subtitles[]` 的 `text` 直接沿用轉錄切好的**短句**（通常 1-2 秒
  一句），不要自己手動合併成長段落——合併過的長句會跟語音對不上
  （踩過這個坑）。
- **選好一個重點片段的大致頭尾之後，不要直接把它當一整段連續
  `keep=true` 丟進去——還要用 `.words.json` 檢查片段內部有沒有明顯
  停頓/贅詞，這是「判斷層」該做的事，不是事後才補的細節**：
  - 讀該片段時間範圍內的逐字時間戳，找相鄰兩個字之間**間隔超過
    約 1 秒**的地方（真正聽得出來的停頓、發語詞卡頓、或講者中途
    重新組織語句），以及單一字時間戳異常長（例如一個字標了
    3-4 秒）的情況——這種通常代表 ASR 把停頓算進了那個字的時間裡，
    實際發音只佔開頭一小段，其餘是空拍。
    自然的語氣停頓（1 秒以內）不用剪，剪過頭語速會變得不自然。
  - 找到要剪掉的停頓後，用**同一套 `clips[]` 交錯 `keep=true`/
    `false` 機制**把這個重點片段拆成好幾小段（跟「抓不連續重點」
    是同一招，只是這次是同一句話內部的切割），拆點抓在停頓前後
    各留約 0.15 秒緩衝，不要切在字的正中間。
  - `subtitles[]`/`broll[]` 是定義在「剪完拼接後的輸出時間軸」，
    不是原始影片時間——同一句字幕的文字如果剛好跨過你新切的停頓點，
    不用把文字拆成兩張字卡，直接讓這句字幕在輸出時間軸上連續顯示
    （字幕本來就不知道底下畫面在這裡跳接過），只要正確換算成
    「拼接後」的秒數即可；只有在停頓真的很長、切掉一大段（例如
    好幾秒）時，才需要把該句字幕拆成兩句分別對應剪輯前後。
  - 如果同一支影片剪出來後使用者反應「最後一個字被切到」，先去查
    `.words.json` 裡那個字的真實結束時間，通常是片段終點抓得太貼
    （緩衝不到 100 毫秒）——`render.py` 也會在每段尾端補一個很短的
    音量淡出防止硬切太突兀，但緩衝時間本身還是要在這裡的判斷階段
    抓對，淡出只是保險，不能取代正確的時間點。
  - **不是只有片段「內部」要查，片段的起點/終點本身也要用
    `.words.json` 核對**——踩過的坑：選片段時只看 `.srt` 的粗略句界，
    起點剛好落在一個被 ASR 判成「單一字詞卻標了 10 秒以上」的糊塗
    區段邊緣（例如把一整句話 + 長停頓 + 人名，全部誤判黏成一個詞的
    時間戳），結果剪出來的片段開頭混進了一段誰也聽不出來、逐字稿也
    抓不到的雜音／人聲。做法：起點/終點抓定後，往前後各看約
    2-3 秒的 `.words.json`，檢查兩件事（缺一不可，只查其中一種會
    漏掉另一種糊塗區）：
    1. **詞條時間戳長度超過 1.5 秒**（正常一個字通常 0.1-0.5 秒）——
       這是明顯的大範圍糊塗區，通常一漏就是好幾秒到十幾秒。
    2. **相鄰詞條時間戳重疊**（後一個詞的 `start` 比前一個詞的
       `end` 還早）——這是更隱蔽的糊塗區，實測踩過：字幕整整偷跑了
       約 1 秒，但那個問題詞條本身的時長只有 0.96 秒，遠低於上面
       1.5 秒的門檻、單看時長完全抓不到，只有比對「這個詞的起點
       是不是比上一個詞的終點還早」才發現——這種重疊代表 ASR 對
       這兩個詞的邊界完全沒對齊，不能相信它給的起點。
    只要中了任何一種，起點/終點要整個往外挪，避開該區間，不要只挪
    幾十毫秒的緩衝就了事，因為問題不是「切太貼」而是「這一帶內容
    本身就不可信」。
  - **驗證方法要分兩種情境，不要混用**：
    - 懷疑「剪出來的片段本身內容不對／混進不該有的話」時，把懷疑
      的那一小段（例如前後各留 10-20 秒）**單獨抓出來、重新轉錄一次**
      去核對——這個做法**可靠**，實測案例：某處被原始全片轉錄誤判
      成一個 12 秒長詞、把裡面真正講到的一句話整個吃掉，單獨抓那一
      小段重新轉錄，不但抓到那句話，連精確的起訖時間戳都清楚呈現。
      **用整支影片重新轉錄一次去驗證則不可靠**——同一套
      ASR 用同樣的方式處理整支影片，大概率在同一個地方再犯同樣的
      錯，驗證不出真正的問題；只有把可疑片段單獨切出來、脫離原本
      整體轉錄的上下文，才有機會讓 ASR 給出不一樣（更準）的結果。
    - 懷疑「字幕時間跟語音對不上（偷跑/搶拍）」時，光看
      `.words.json` 不夠，因為問題可能就出在 `.words.json` 本身的
      時間戳不準——要直接把**剪好的那段成品**（`04_cuts/render_work/
      beat_*.mp4` 或最終輸出）重新轉錄，拿逐字時間戳去跟
      `edit_state.json` 裡宣稱的 `start`/`end` 比對，才是真正可靠
      的核對方式。

把判斷結果寫成 `06_meta/edit_state.json`，`status` 先維持
`"draft"`。完整 schema 範例見 `edit_state.example.json`，
容易搞混的欄位說明見 `README.md`「edit_state.json 重點欄位」。

### 第 5 步：執行剪輯（呼叫本機工具，不要自己模擬）

```bash
python render.py "projects/<專案名稱>/06_meta/edit_state.json"
```

`render.py` 會依序：剪掉 `keep:false` 的片段、把逐句字幕燒成 ASS
（`libass`，不是逐句 PNG 疊圖，字型/顏色/描邊/陰影都在
`subtitle_style` 設定）、用 ImageMagick 產生標題卡／CTA 卡、套用
B-roll 疊圖、混音，輸出到 `05_render/<專案名稱>_<時間戳>.mp4`——
**每次出片都是另存新檔，不會覆蓋舊版本**。

剪每一段 `keep=true` 的片段時，`render.py` 會自動用 `silencedetect`
掃一次那段有沒有超過 1.5 秒的異常靜音，發現的話會印出 `[警告]`
（不會中止），**你一定要看終端機輸出，不能只看程式跑完 exit code
是 0 就當作沒事**——exit code 0 只代表 ffmpeg 指令沒有崩潰，不代表
剪出來的內容是對的。

### 第 5.5 步：出片後，先驗證再交付——不要憑推理就宣稱「應該修好了」

**這是踩過真實的坑才加的一步，務必照做**：曾經因為懷疑某個問題的
成因（例如尋帶不精準），沒有實際驗證就動手改了 `render.py` 直接
出片給使用者，結果那個「修法」本身是錯的，還悄悄讓每段影片尾端
掉了好幾秒的聲音——而且原本懷疑的問題根本不是那個成因造成的。
Claude 自己聽不到、看不到渲染出來的影片，**任何「我猜是 O 造成的，
已經修好了」都只是未驗證的假設，說出口前要先用工具實際驗證**：

- 出片後如果終端機有印出上面說的 `[警告]`，先處理掉，不要無視。
- **出片後、交付給使用者前，一定要跑 `verify_render.py` 做字幕同步
  自動驗證，這不是選配步驟**：

  ```bash
  python verify_render.py "projects/<專案名稱>/06_meta/edit_state.json"
  ```

  這支腳本會把最新那支成品重新轉錄一次，拿「真正聽得到」的逐字時間
  跟 `subtitles[]` 宣稱的 `start` 比對，超過 0.4 秒差距就列出來——
  這是**機械化的安全網**，不是「建議做」，因為實測發生過：只針對
  使用者具體反映的那幾句字幕手動修正，改完自己覺得沒問題就交付，
  結果同一支影片裡還有好幾句完全沒被使用者發現、也沒被人工檢查到
  的字幕偷跑（超過1秒），是這支腳本自動掃出來的。人工「憑印象覺得
  應該都對了」不可靠，每次出片都要讓這支腳本實際跑過一遍。
  - 需要 `GROQ_API_KEY`。沒設定的話腳本會印提醒並直接跳過（不會擋
    住出片流程），但這種情況要老實告訴使用者「這版沒辦法自動驗證
    字幕同步，需要人工聽過確認」，不要略過不提。
  - 腳本印出的每一句警告都要處理（回頭修正 `subtitles[]` 對應的
    `start`/`end`，通常要查 `.words.json` 或重新轉錄那一小段來抓
    真正的時間），改完重新出片、再跑一次驗證，直到沒有警告為止，
    才算真的完成。
- 使用者反映的其他類問題（聲音消失、內容跑掉、聽到不該出現的字句）
  **要能重現才能下定論成因**，`verify_render.py` 不會抓到這類問題
  （它只比對文字時間，不管內容對不對），還是要另外用這些手段：
  - 用 `ffmpeg -i <檔案> -af silencedetect=noise=-35dB:d=1.0 -f null -`
    掃異常靜音（看 stderr 裡的 `silence_start`/`silence_duration`）。
  - 把可疑的成品片段單獨抓出來重新轉錄，跟預期內容比對（做法跟
    上面「起點/終點也要核對」那段講的一樣）。
  - 懷疑是某個修改造成的，就把「改之前」跟「改之後」兩版都各剪一小
    段出來做同樣的檢查再比較，不要單靠邏輯推理判斷哪個版本才是對的。
- 只有實際跑過上述驗證、確認乾淨，才能跟使用者說「已經修好了」；
  驗證不了的部分要老實說「這部分我沒辦法直接驗證，麻煩你看過確認」，
  不要用聽起來合理的推論包裝成「已解決」。

### 第 6 步：給使用者看成品、視需要放行給 GUI 微調

先把這版成品交給使用者確認（片長、剪了哪些內容、配了哪些 B-roll）。
使用者確認可以之後，才把該 `edit_state.json` 的 `status` 改成
`"approved"`——這一步不是自動的，你自己實驗/測試用的 `edit_state`
檔案要一直留在 `"draft"`，不要手滑改成 approved 混進使用者要挑的
清單（`caption_editor/` GUI 的下拉選單只列 `status=="approved"` 的
檔案）。

改成 approved 之後，使用者可以自己開網頁 GUI 微調字幕逐字校正/
斷句、排版、字卡文字，改完直接在網頁上按「產生影片」重新出片：

```bash
python caption_editor/server.py
# 開瀏覽器 http://localhost:8770
```

### 第 7 步：交付成品

跟使用者說明最終檔案位置（`05_render/` 底下最新那個時間戳版本）、
片長、大概剪掉了哪些內容、配了哪些 B-roll，並更新 `06_meta/` 裡的
狀態紀錄。

## 兩種剪輯模式

見第 4 步說明；差別只在「你怎麼決定要保留哪些時間區間」，兩種都是
同一套 `clips[]` + `render.py` 機制，不需要不同的程式碼路徑。

## 版面

目前只有一種固定版面（`talking_head_3zone`）：畫面分三區——上方
標題卡、中間人物說話畫面、下方 CTA 結尾卡，字幕燒在畫面下段偏上
位置。`edit_state.json` 裡的 `template` 欄位目前只是紀錄用途，
`render.py` 還沒有依它切換不同版型。

## 資料夾結構

每個專案在 `projects/<專案名稱>/` 底下，固定六個子
資料夾：

```
01_source/       原始影片副本（不動原檔）
02_transcript/   逐句 SRT／逐字時間戳 .words.json
03_broll/        Pexels 抓回來的補充畫面素材
04_cuts/         中間檔（若有用到）
05_render/       最終成品（版本化檔名，每次出片另存新檔）
06_meta/         edit_state.json，記錄剪輯點/字幕/字卡/狀態
```

如果使用者每天剪很多支，長期只需保留 `02_transcript`（檔案很小）
與 `06_meta`，`01_source`／`03_broll`／`04_cuts` 這些體積大的中間檔
可以在成品確認沒問題後清掉。

## 找 B-roll（Pexels）

使用者需要先設定 `PEXELS_API_KEY` 環境變數。只在使用者第 2 步要求
配 B-roll 時才做這件事，抓幾段、多密集照第 2 步問到的密集程度來，
不要自己猜：

- 用判斷出的英文關鍵字查詢（例如講「時間管理」的段落可以查
  `"calendar planning"` 或 `"clock time management"`）。
- 優先選橫向或直向皆有素材可裁切的影片，裁切成 9:16 置中。
- 每個 B-roll 片段抓 3-6 秒即可，避免喧賓奪主蓋過主講畫面太久；
  段數多寡依使用者要的密集程度決定，密度太高會喧賓奪主、太低又
  等於沒配。

## 注意事項

- 每一步呼叫外部工具（Whisper/Groq／ffmpeg／ImageMagick／Pexels
  API）都是明確的 shell 指令或 API call，絕對不要嘗試「自己用文字
  描述」去生成剪輯結果——你的角色是判斷與下指令，不是自己當剪輯
  軟體。
- 若轉錄有明顯同音字錯誤（尤其是專有名詞、統編、公司名），寫
  `edit_state.json` 前先過一遍 `.srt` 校正，不確定原音在講什麼的
  地方抓一小段音檔片段讓使用者確認，不要用猜的直接改。
- 更細的技術眉角（ASS 顏色格式、Windows 換行符號陷阱、字卡 emoji
  限制、逐字編輯器的時間格粒度規則等）都在
  `README.md`，改動核心邏輯時兩邊要一起維護，避免這份
  技能檔又跟實作分岔。
